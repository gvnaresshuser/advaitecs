Scenario 08: useEffect Debugging — Repeated API Calls and Missing Dependencies

This is especially useful for your React full-stack training because students will learn to connect three things: React rendering, useEffect dependencies, and repeated requests in Chrome DevTools → Network.
We'll use your existing Express backend on port 5000 and Vite proxy, so no additional backend is required.

src/scenarios/use-effect/ProblemComponent.tsx
This component deliberately omits the dependency array. To keep the classroom demonstration safe, it caps the repeated requests at five.

What is wrong?
The effect runs after every render because it has no dependency array.
Each successful request calls setUsers(), causing another render. The effect then runs again, triggering another request until the five-request limit is reached.
The useRef counter limits this teaching example without introducing another state dependency into the effect.

src/scenarios/use-effect/SolutionComponent.tsx
Here, the effect uses an empty dependency array and an AbortController to cancel the request if the component unmounts.

The empty dependency array expresses that this effect doesn't need to respond to changing props or state. The cleanup cancels an in-flight request when necessary.
Important: In React Strict Mode, development may perform an additional effect setup-and-cleanup cycle. This can result in an extra request attempt, so don't assume that two requests automatically indicate an infinite loop.

rc/scenarios/use-effect/UseEffectScenario.tsx

Expected observations:
Observation			Problem							Solution
Dependency array	Missing	Empty array
API requests		Repeated, capped at five		Initial effect execution, with possible Strict Mode development replay
Console				Repeated effect logs			Effect execution logs
UI					Users may be loaded repeatedly	Users loaded with a cleanup function
Cleanup				None							Aborts an in-flight request

Understand the bug
The incorrect condition is:

Each scenario can have its own files and its own debugging instructions. We won't put every example into one enormous component.
4. How each scenario will work
For example, the API Data Not Displaying scenario will contain:
Problem Code
The API returns { users: [...] }, but the component assigns the complete response object to a state variable expected to contain an array.

Student Investigation
Open Network → Fetch/XHR → Response. Confirm that the API response contains a users property. Then inspect the component in Sources or React Developer Tools.

Solution Code
Extract the array from response.data.users and update the state with the correct value.

Important implementation decisions
- Console scenarios: Use deliberate runtime errors and meaningful diagnostic messages.
- Network scenarios: I recommend a small Express mock API alongside the frontend. This lets us reliably demonstrate 200, 400, 401, 404, 500, delayed responses, and incorrect response structures.
- Sources scenarios: Keep the actual .tsx files easy to locate through Vite source maps.
- React Developer Tools: Use real component props, state, and hooks rather than simulated inspector data.
- useEffect scenarios: Demonstrate missing dependencies, incorrect dependencies, cleanup, and repeated requests separately.
- Responsive scenarios: Provide deliberately broken and corrected Tailwind layouts that students can test at different viewport widths.
- Safe demonstrations: Isolate intentional runtime errors so one broken component doesn't bring down the entire lab.
5. Suggested development order
Implementation checklist
0 of 6

[ ] Create the dashboard and navigation
App layout, sidebar, scenario list, and responsive Tailwind styling.

[ ] Build the Console exercises
Undefined data, event-handler errors, and runtime debugging.

[ ] Build the Network exercises
Mock Express API, failed requests, incorrect responses, and loading states.

[ ] Build the Elements and Sources exercises
CSS problems, layout issues, breakpoints, and step-by-step execution.

[ ] Build the React debugging exercises
Props, state, useEffect, and repeated API calls.

[ ] Add advanced exercises
Forms, React Query cache, TypeScript build errors, and Profiler.

My recommendation: Let's build this step by step, starting with the dashboard and navigation, then implement and test each scenario before moving to the next. That way, you'll have a working training project throughout development instead of receiving a large amount of code that is difficult to troubleshoot.

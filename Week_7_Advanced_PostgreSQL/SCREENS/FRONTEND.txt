Yes. Let’s implement Aggregate Functions + GROUP BY next.
1. PostgreSQL concept first
We want to calculate statistics for each department:
COUNT() → number of employees
AVG()   → average salary
MIN()   → minimum salary
MAX()   → maximum salary

Our SQL is already available in the backend:
SELECT
  d.department_id,
  d.department_name,
  COUNT(e.employee_id) AS employee_count,
  ROUND(AVG(e.salary), 2) AS average_salary,
  MIN(e.salary) AS minimum_salary,
  MAX(e.salary) AS maximum_salary
FROM departments_advaitecs_advpgsql d
LEFT JOIN employees_advaitecs_advpgsql e
  ON d.department_id = e.department_id
GROUP BY
  d.department_id,
  d.department_name
ORDER BY d.department_id;

Why GROUP BY?
Without GROUP BY, PostgreSQL would calculate statistics for all employees together.
With:
GROUP BY d.department_id, d.department_name

PostgreSQL creates one group for each department.
For our data, conceptually:
Development
   Employees: Ravi, Priya, Meena

Testing
   Employee: Arun

HR
   Employee: Sneha

Database
   Employee: Kiran

Then PostgreSQL calculates COUNT, AVG, MIN, and MAX separately for each group.

----------------------------------------------------
GROUP BY + HAVING now.
1. PostgreSQL concept
We want to find departments having more than one employee.
The SQL is:
SELECT
  d.department_name,
  COUNT(e.employee_id) AS employee_count
FROM departments_advaitecs_advpgsql d
INNER JOIN employees_advaitecs_advpgsql e
  ON d.department_id = e.department_id
GROUP BY
  d.department_id,
  d.department_name
HAVING COUNT(e.employee_id) > 1
ORDER BY employee_count DESC;

Important teaching point
WHERE
  ↓
filters individual rows

GROUP BY
  ↓
creates groups

HAVING
  ↓
filters the groups

For our data:
Development → 3 employees  ✅
Testing     → 1 employee   ❌
HR          → 1 employee   ❌
Database    → 1 employee   ❌

Therefore, only Development should appear.

Absolutely. Let’s implement Employee Pagination now.
1. PostgreSQL concept first
Pagination allows us to retrieve only a small portion of records instead of loading the entire table.
Our SQL:
SELECT
    employee_id,
    employee_name,
    email,
    salary,
    department_id
FROM employees_advaitecs_advpgsql
ORDER BY employee_id
LIMIT 3
OFFSET 0;

The important formula is:
OFFSET = (page - 1) × limit

Therefore:
Page 1 → LIMIT 3 OFFSET 0
Page 2 → LIMIT 3 OFFSET 3

Because email is defined as:
email VARCHAR(150) UNIQUE NOT NULL

PostgreSQL automatically creates a unique index for the email column.
We can verify that with:
SELECT
    indexname,
    indexdef
FROM pg_indexes
WHERE tablename = 'employees_advaitecs_advpgsql';

You should see:

INDEX + EXPLAIN ANALYZE demonstration
----------------------------------------------------
One important teaching point first: because our table has only 6 employees, PostgreSQL may choose a Sequential Scan even when an index exists. That is normal—the planner chooses the cheapest plan for the table size.
For this demo, I recommend showing the SQL and the execution plan in the UI.
1. PostgreSQL concept
First, create/verify the employee-name index:
CREATE INDEX IF NOT EXISTS idx_employee_name_advaitecs_advpgsql
ON employees_advaitecs_advpgsql(employee_name);

Then:
EXPLAIN
SELECT
    employee_id,
    employee_name,
    email,
    salary
FROM employees_advaitecs_advpgsql
WHERE employee_name = 'Ravi';

And:
EXPLAIN ANALYZE
SELECT
    employee_id,
    employee_name,
    email,
    salary
FROM employees_advaitecs_advpgsql
WHERE employee_name = 'Ravi';

2. Important distinction
EXPLAIN
   ↓
Shows the planned execution strategy
Does NOT execute the query

EXPLAIN ANALYZE
   ↓
Actually executes the query
Shows actual execution statistics

For example, you may see:
Seq Scan on employees_advaitecs_advpgsql

rather than:
Index Scan using idx_employee_name_advaitecs_advpgsql

With only six rows, PostgreSQL can reasonably decide that scanning the small table is cheaper than using the index.
